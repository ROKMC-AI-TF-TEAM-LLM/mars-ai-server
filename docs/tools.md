# tools.md — 도구 설계 지침과 추가 후보

에이전트가 고를 수 있는 **행동(도구)** 의 설계 판단과 후보 목록을 관리한다.

- **코드 추가 절차**는 `src/ax_rag/query_graph/tools.py` 모듈 docstring이 소유한다 (6단계)
- 이 문서는 그 앞 단계 — **"애초에 도구로 만들 것인가"** 와 **무엇을 다음에 만들 것인가**
- 실측 근거는 `docs/experiments.md`, 그래프 배선은 `docs/architecture.md` §4

---

## 1. 현재 도구

| 행동 이름 | intent | 종류 | 실행 시점 | 강제 지정 | 결정적 매처 |
|---|---|---|---|---|---|
| `search_documents` | `DOC_SEARCH` | 검색 | inline | ⭕ | — |
| `discharge_days` | `DISCHARGE_DAYS` | **결정적 코드** | inline | ⭕ | ⭕ |
| `draft_document` | `HWP_DRAFT` | LLM 생성 + 파일 | inline | ⭕ | ✕ |
| `export_hwp` | `HWP_EXPORT` | **결정적 코드** + 파일 | **deferred** | ⭕ | ⭕ |
| `finish` | — | 루프 종료 | — | — | — |

`search_documents`와 `finish`는 도구가 아니라 루프의 기본 행동이라 `TOOL_NODES`에 없다.
잡담·자기소개는 도구가 아니라 **도구 없이 finish** → `direct_answer` 노드가 담당한다.

### 실행 시점 (phase)

| | 언제 | 검증 실패 시 |
|---|---|---|
| `inline` | 루프 안에서 즉시 실행, 결과를 관측으로 반환 | 실행됨 (이미 실행된 뒤) |
| `deferred` | verify 통과 **후** 실행 | **실행 안 됨** (fail-closed) |

`POST_SEARCH_TOOLS` 포함 여부로 자동 결정된다. "방금 만든 답변"을 입력으로 쓰는
도구(파일 저장)는 반드시 `deferred`여야 한다 — 검증 못 받은 답변을 파일로 만들지 않는다.

## 2. 도구로 만들 것 / 만들지 말 것

### 값이 큰 도구의 조건

> **LLM이 틀리고 코드가 맞는 일**을 하는 도구가 가장 값이 크다.

`discharge_days`가 그 원형이다. 날짜 산술은 7B가 틀리지만 코드는 항상 맞고,
결과가 결정적이라 verify를 거치지 않아도 안전하다.

우선순위 판단은 이 순서로 한다:

1. **결정적인가** — 같은 입력에 같은 출력인가. 그렇다면 검증 밖이어도 안전하다
2. **측정된 실패 구간을 겨냥하는가** — 검색은 이미 96.2% 정확하다
   (`experiments.md` 실험 10). 실패는 **찾은 근거로 답을 못 만드는 구간**에 있다
3. **선행 조건이 없는가** — 인덱싱 변경·새 데이터가 필요하면 뒤로 민다
4. **비용이 작은가** — LLM 호출 0회, HTTP 왕복 최소

### 만들지 말 것

| 유형 | 이유 |
|---|---|
| 외부 API·웹 검색 | **에어갭 위반** (CLAUDE.md 절대 규칙 1·2) |
| 메일 발송·결재 상신 등 | 되돌릴 수 없는 외부 작용. 이 시스템의 범위 밖 |
| `summarize` · `translate` 같은 LLM 도구 | generate가 할 일이다. 도구로 빼면 **verify가 닿지 않는 생성 면적만 늘어난다** |
| "규정 해석" 도구 | 근거 없는 판단을 권위 있게 포장하게 된다 |
| 검색 범위를 인자로 받는 도구 | ACL·도메인은 **상태가 정한다**. LLM이 정하는 경로를 만들지 않는다 (CLAUDE.md 보안 규칙) |

마지막에서 두 번째가 핵심 원칙이다 — **LLM 호출을 도구로 만들수록 검증이 닿지
않는 면적이 늘어난다.** 지금 구조가 안전한 이유는 답변 생성이 `generate` + `verify`
한 곳에 모여 있기 때문이다.

### 설계 체크리스트 (코드 작성 전)

- [ ] 결정적 코드인가, LLM 생성인가. LLM 생성이면 **창작 범위를 무엇으로 좁히는가**
- [ ] `inline`인가 `deferred`인가 (확정 답변을 입력으로 쓰면 deferred)
- [ ] `FORCIBLE_TOOLS`에 넣어도 되는가 — **강제로 업무 질문이 들어와도 안전한가**
      (⚠️ SMALLTALK은 강제 유입 시 모델이 규정을 지어내는 것이 실측돼 **제외**돼 있다)
- [ ] 결정적 매처로 잡을 수 있는가 (LLM 호출 0회 경로)
- [ ] 관측이 `MAX_OBSERVATION_CHARS`(400자)에 들어가는가
- [ ] 근거를 늘리는 도구라면 **16K 예산**을 넘지 않는가 (`retrieval.merge_chunks` 절단)
- [ ] ACL을 우회하지 않는가

## 3. 후보 목록

상태: `제안` → `검토중` → `착수` → `완료` / `보류` / `기각`

### 3-1. `read_more` — 근거 청크의 앞뒤 더 읽기 · **제안 (1순위)**

**문제**: 리랭커가 고른 청크에 조항 본문은 있는데 **조건·예외·기한이 다음 항에 있어서**
verify가 반려하는 패턴이 반복된다 (`synth-03`의 "신청 방법" 등).

**설계**
- 검색이 아니라 **정확 조회**: `source_doc` + `chunk_index ± N` 으로 Milvus `query`
- 스키마에 `chunk_index`·`source_doc`가 **이미 있다** (인덱싱 변경 불필요)
- 인자: `source_doc`, `chunk_index` (또는 근거 목록의 순번)
- phase: `inline` / 강제 지정: 불필요 / 매처: 불필요

**비용**: Milvus query 1회. **임베딩·리랭커 호출 없음** — 검색보다 훨씬 싸다

**위험**
- 근거가 늘어 컨텍스트 예산 압박 → `merge_chunks` 절단과의 상호작용을 확인할 것
- 리랭크 점수가 없는 청크가 섞인다 (정확 조회라 점수가 없음) → 병합 정렬에서 뒤로 밀림.
  **점수 부여 방식을 정해야 한다**

**선행 확인 (착수 전 필수)**
> 리랭크 뒤에 **부모 청크 치환(1000토큰)** 이 이미 들어가 문맥이 어느 정도 확보된다.
> 따라서 "부모 청크로도 안 잡히는 케이스가 실제로 얼마나 되는지"를 먼저 재야
> 이 도구의 이득을 알 수 있다. 안 재고 만들면 `experiments.md` §5의 실수
> ("측정 없이 표적을 정했다")를 반복하게 된다.

---

### 3-2. `list_documents` — 적재된 문서 목록 조회 · **제안 (2순위)**

**문제** 두 가지를 동시에 해결한다.
1. 사용자 질문 *"무슨 문서 갖고 있어?"* 에 답할 방법이 지금 없다
2. **검색 0건일 때의 판단 재료**가 없다 — 지금은 곧바로 `knowledge_answer`
   (검증 없는 지식 답변)로 떨어진다. 목록을 보고 다시 검색하면 살릴 수 있는 케이스가 있다

**설계**
- phase: `inline` / 매처: 가능 ("무슨 문서", "문서 목록" 등)

**🚨 선행 필수 — 기존 `list_documents()`는 ACL을 적용하지 않는다 (확인 완료)**
> `vectorstore.list_documents()`는 `fetch_all_children()`로 **전체를 긁어** 집계하며
> 사용자 부서로 거르지 않는다. `GET /documents`도 `user_department`를 받지 않는
> **관리·디버깅용** 엔드포인트라, 지금 형태 그대로는 정상이다
> (호출자 통제는 미들웨어 몫).
>
> 그러나 **이것을 그대로 에이전트 도구로 배선하면 ACL 우회 경로가 된다** —
> 부서 제한(`visibility=DEPT_ONLY`) 문서명이 모든 사용자에게 노출된다.
> 본문을 못 봐도 **문서명만으로 정보가 새는** 경우가 있다 (특정 작전·부대 명칭 등).
>
> 따라서 도구화하려면 **부서 인자를 받아 거르는 별도 함수**를 먼저 만든다.
> 관리용 `list_documents()`는 그대로 두고, 도구는 그 필터링 버전만 쓴다.
> 이때도 부서는 **상태에서** 읽는다 (LLM 인자로 받지 않는다).

**추가 검토**: 문서가 많으면 관측 400자에 안 들어간다 → 도메인별 건수 요약 또는
질문과 관련된 것만 추리는 방식이 필요하다.

---

### 3-3. `lookup_article` — 조 번호로 원문 정확 조회 · **제안 (3순위)**

**문제**: *"○○ 훈령 제15조 원문 보여줘"* 는 의미 검색이 아니라 **키 조회**다.
벡터 검색으로 하면 인접 조항이 섞인다.

**선행 조건**: 청크에 **조 번호 메타데이터가 없다** → 인덱싱 단계 변경 필요.
이것 때문에 1·2순위보다 뒤에 둔다.

**부수 이득**: 조 번호 메타데이터가 생기면 답변의 조항 인용 정확도 검증에도 쓸 수 있다.

---

### 3-4. `find_contact` — 담당 부서·연락처 안내 · **보류 (데이터 필요)**

**문제**: fallback이 *"담당 부서에 직접 문의해 주세요"* 라고 하면서 정작
**어느 부서인지 말하지 못한다.** 실패 답변의 체감 품질에 직결된다.

**선행 조건**: 업무 ↔ 담당 부서 매핑 테이블. 있으면 완전한 결정적 도구가 된다.

---

### 3-5. `fill_form` — 정형 서식 채우기 · **보류 (서식 파일 필요)**

**문제**: `draft_document`는 자유 초안이라 서식이 흔들린다. 휴가원·출장신청서처럼
양식이 정해진 문서는 **템플릿에 값만 꽂는** 편이 정확하고, LLM은 값 추출만 하면 된다.

**선행 조건**: HWPX 서식 템플릿 반입.
**이점**: LLM의 창작 범위가 "값 추출"로 줄어 `draft_document`보다 안전하다.

---

### 3-6. `calc_days` — 일반 날짜·기간 계산 · **제안 (낮음)**

`discharge_days`의 일반화. *"3월 15일부터 6개월이면 언제까지?"*,
*"이월 연차 사용기한이 며칠 남았나"*. 공휴일 표가 있으면 근무일 계산까지 가능.

**주의**: `discharge_days`와 매처가 겹치지 않게 할 것.

## 4. 기각된 후보

같은 논의를 반복하지 않기 위해 남긴다.

| 후보 | 기각 사유 |
|---|---|
| 웹 검색 / 외부 법령 API | 에어갭 위반. 예외 없음 |
| `smalltalk` 을 강제 지정 가능한 도구로 | 강제 경로로 업무 질문이 들어오면 verify 밖에서 모델이 규정을 지어내는 것을 실측. 프롬프트로 막히지 않아 **구조적으로 차단**했다 (`tools.FORCIBLE_TOOLS`) |
| `summarize` / `rewrite` 도구 | generate가 할 일. verify 밖 생성 면적만 늘어난다 |
| 검색 범위(부서·도메인)를 LLM 인자로 받는 도구 | ACL을 LLM이 정하게 된다 (CLAUDE.md 보안 규칙) |

````markdown
### 3-N. `도구이름` — 한 줄 설명 · **상태**

**설계**
- 결정적 코드 / LLM 생성 (LLM이면 창작 범위를 무엇으로 좁히는가)
- phase: inline / deferred
- 인자, 재사용할 기존 코드

**비용**: LLM 호출 n회, HTTP 왕복 n회

**위험**: 예산·ACL·검증 우회 관점에서

**선행 조건**: 없으면 "없음"
````
